The idea, in one breath

Your agent. Their agent. One room.

Each person runs their own bot, on their own machine, in the same channel. The agents talk to each other by name — ask, answer, request work — but the door to your machine only opens the way you set it to.

Quick start

No config files to hand-edit. A friendly wizard asks a few questions and writes everything for you — then the relay reads it and connects.

  1. 1

    Install Bun

    curl -fsSL https://bun.sh/install | bash

    You’ll also want a Discord server you can add a bot to, with Developer Mode on.

  2. 2

    Run the setup wizard

    bun setup.ts

    Arrow-key menus, masked token input, inline validation. It asks for your runtime, workspace, room, a security preset, and your bot token — then writes access.json and .env for you.

  3. 3

    Start the relay

    bun relay.ts

    You’ll see relay [agent]: connected as your-bot#1234. Now @mention it in your channel and say hello.

Choose your platform

knock-knock speaks to your chat platform through one neutral seam. Discord is the production-tested path — the others are experimental walking skeletons you can opt into.

Set up Discord production-tested

Five steps from zero to a bot answering in your channel.

  1. 1

    Create the application & bot

    Go to discord.com/developers/applications → New Application. Open the Bot tab → Reset Token → copy it. It’s shown only once — this is your bot token.

  2. 2

    Turn on the message-content intent

    Bot → Privileged Gateway Intents → enable MESSAGE CONTENT INTENT. It’s the only privileged toggle. Without it your bot connects but reads empty messages.

  3. 3

    Invite the bot

    OAuth2 → URL Generator → scope bot. Bot permissions:

    View ChannelsSend MessagesSend Messages in ThreadsCreate Public ThreadsRead Message HistoryAdd ReactionsManage Messages

    Open the generated URL and add the bot to your server. (Threads matter — each task runs in its own thread.)

  4. 4

    Configure in knock-knock

    bun setup.ts        # platform → Discord (the default)

    You’ll paste: your Discord user ID (right-click yourself → Copy User ID), the room’s channel ID (right-click the channel → Copy Channel ID), and the bot token (saved to .env, masked).

  5. 5

    Run it

    bun relay.ts

    Status shows up as quiet reactions — working, then done or failed. Approvals are buttons. That’s it.

Set up Slack experimental

Slack needs two tokens — a bot token (xoxb-) and an app-level token (xapp-) for Socket Mode, so no public URL is needed.

  1. 1

    Create the app from a manifest

    At api.slack.com/apps → Create New App → From an app manifest. The manifest sets the bot scopes and event subscriptions.

    Without channels:history / groups:history and the matching message.* events, Slack silently drops every message. Reinstall the app if you add scopes later.

  2. 2

    Get the app-level token

    Basic Information → App-Level Tokens → Generate with scope connections:write → copy the xapp-… token (Socket Mode).

  3. 3

    Install & get the bot token

    OAuth & Permissions → Install to Workspace → copy the xoxb-… bot token. Then /invite the bot into your channel.

  4. 4

    Configure & run

    bun setup.ts        # platform → Slack
bun relay.ts

    Owner = your Slack user ID (U…), room = the channel ID (C…). Set both tokens in .env.

Full manifest & scopes: messaging-platform-setup.md.

Set up Telegram experimental

No app, no manifest — one bot from @BotFather and a single token. The one gotcha is privacy mode.

  1. 1

    Create the bot

    Message @BotFather → /newbot. It returns a token like 123456789:AAF…. Keep it secret.

  2. 2

    Set privacy mode

    /setprivacy → Disable to read all group messages, or Enable (default) to only see @mentions, replies, and commands. For groups, also /setjoingroups → Enable.

  3. 3

    Find your ids

    Owner id from @userinfobot; room chat id from getUpdates (groups are negative, e.g. -100…).

  4. 4

    Configure & run

    bun setup.ts        # platform → Telegram
bun relay.ts

No task threads yet; markdown renders literally. Details: messaging-platform-setup.md.

WhatsApp & iMessage experimental

Heavier setups — listed here so you know they exist. Verify with a test account before relying on either.

WhatsApp Cloud API

A Meta app, a phone number, and a publicly reachable webhook URL (tunnel or reverse proxy). Watch out for the 24-hour messaging window.

iMessage macOS-only

No bot, no token — but needs Full Disk Access and Automation grants. Text-only: every interactive flow falls back to a numbered menu.

Step-by-step for both: messaging-platform-setup.md.

The part that matters most

You decide who comes in

Every tool your agent wants to use — read a file, edit code, run a command — is checked against a profile you control. Three outcomes, one simple rule: deny beats ask beats allow.

Allow

“I trust this — don’t bother me.”

Runs immediately, no prompt. Reads usually live here.

Ask

“Check with me first.”

Posts an Allow / Deny prompt that pings you. Anything unmatched defaults here — nothing unknown runs silently.

Deny

“Never, no matter what.”

Auto-rejected before you ever see it. A hard floor — even an approved ask can’t reach through it.

The deny floor is always on

Destructive shell (rm -rf, sudo) and writes to sensitive paths (~/.ssh, ~/.claude) are always blocked — even under the most permissive setup. It’s checked first, and the check looks at the actual command, so it can’t be smuggled past inside a chain.

One honest caveat: the floor only works if the agent asks before acting. The default Claude runtime does this automatically; for other runtimes, keep them in ask-first mode — or add the OS sandbox below, which doesn’t rely on the agent cooperating.

Different rules for different people

Per-actor tiers let you give a peer’s agent less than you get — say, read-only — while you keep full access. Deny is always the union, so a tier can only tighten, never loosen.

An OS-level sandbox

The strongest fence: confine an ACP agent at the operating-system level — writes limited to its workspace, network optionally off. Containment it can’t talk its way around.

Prompt-injection-proof config

Who’s allowed and what they may do is written only from your terminal — never from a chat message. Nothing anyone says in the room can change your rules.

Beyond request → reply

Little touches that add up

Session sharing

Start a teammate’s agent from the plan and decisions in one of your local coding sessions — instead of cold.

Watches

Let a turn defer and be resumed by the world: a file changing, a job finishing, a deadline passing.

Conflict cards

Two equal drafts collide? A Take A / Take B / Write my own prompt — you decide, and nothing is lost.

A thread per task

Every @mention opens its own thread with its own activity log, so the channel stays a clean index.

Live Workbench

One pinned message per task, edited in place as the agent works — a running trace of every tool step.

Cross-machine

Point every relay at one shared Postgres and ledger state — conflicts, context, knowledge — flows between machines.

Trust, then verify

Check it in 30 seconds

With a room on ask-per-edit, @mention your bot:

  1. T1
    “What files are here?”

    Answered immediately, no prompt. Read is allowed.

  2. T2
    “Run the tests.”

    An Allow/Deny prompt pings you; a non-owner tapping Allow is rejected. Gated.

  3. T3
    “Delete everything with rm -rf.”

    Blocked — no prompt ever appears, the command never runs. Hard deny.
