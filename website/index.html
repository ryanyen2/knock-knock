Watch one request travel the channel

  1. It starts in a shared channel

    Everyone runs their own agent on their own machine, in one channel. Maya hosts the GPU box. You and Devin build against it.

  2. Anyone can knock

    An @mention to another person's agent is a request. It cannot reach into their machine on its own.

  3. A thread per task

    Each request opens its own thread with its own activity log, so the channel stays a clean index.

  4. Work happens at home

    The agent runs in its owner's workspace, under its owner's rules. The Workbench shows its plan filling in — ○ planned, ◐ in progress, ✓ done — above every step as it goes.

  5. You decide who comes in

    Anything that changes the machine waits for the owner's Allow. The prompt pings only the owner.

  6. Approved once, not forever

    Allow runs the command a single time. The next one asks again. Approval never becomes a standing key.

  7. The deny floor never blinks

    Destructive commands are blocked before anyone sees them. It reads the real command, so it can't be smuggled past in a chain.

  8. Everything is on the record

    Every reply carries an audit line of exactly what ran, on whose machine, and what was denied.

Control is the product.

Every tool an agent reaches for is checked against a profile you own. Three outcomes, one rule: deny beats ask beats allow.

allow

“I trust this. Don't ask.” Reads usually live here. Runs with no prompt.

ask

“Check with me first.” Posts an Allow / Deny that pings you. Anything unknown defaults here.

deny

“Never, no matter what.” Auto-rejected before you see it. Even an approved ask can't reach through.

The deny floor is always on

Destructive shell (rm -rf, sudo), writes to sensitive paths (~/.ssh), and reading or sharing any credential file (.env, *.key, ~/.aws) are blocked under even the most permissive setup. Checked first, against the real command.

One honest caveat: the floor only holds if the agent asks before acting. The default Claude runtime does. For others, keep ask-first mode, or add the OS sandbox.

Different rules for different people

Give a peer's agent less than you get, say read-only, while you keep full access. Deny is always the union, so a tier can only tighten.

An OS-level sandbox

The strongest fence: confine an agent at the operating-system level. Writes limited to its workspace, network optionally off. Containment it can't talk its way around.

Prompt-injection-proof config

Who's allowed, and what they may do, is written only from your terminal. Never from a chat message. Nothing said in the channel can change your rules.

Dial it to your comfort.

Four presets, from a read-only door to fast-and-fenced. Pick one in knock-knock setup. Every level keeps the deny floor.

Strict, a read-only door

For a research bot, or letting an untrusted peer's agent reach yours. It can look, never touch.

  • Reads allow
  • Edits & writes deny
  • Shell deny

Best for untrusted collaborators, public research.

resulting profile (floor still applies)
{
  "allow": ["Read(**)"],
  "ask":   [],
  "deny":  ["Edit(**)", "Write(**)", "Bash(*)", "FileShare(**)"]
}

Ask-per-edit, the safe default

You approve every change. The recommended starting point for almost everyone.

  • Reads allow
  • Edits & writes ask
  • Shell ask

Best for day-to-day work, first time out.

resulting profile (floor still applies)
{
  "allow": ["Read(**)"],
  "ask":   ["Edit(**)", "Write(**)", "Bash(*)", "FileShare(**)"],
  "deny":  ["Bash(rm -rf *)", "Bash(sudo *)", "Read(**/.env)", "FileShare(**/.env)"]
}

Auto, trusted solo work

Edits flow without prompts. Shell commands still wait for your nod.

  • Reads allow
  • Edits & writes allow
  • Shell ask

Best for solo flow on a project you trust.

resulting profile (floor still applies)
{
  "allow": ["Read(**)", "Edit(**)", "Write(**)"],
  "ask":   ["Bash(*)", "FileShare(**)"],
  "deny":  ["Bash(rm -rf *)", "Bash(sudo *)", "Read(**/.env)", "FileShare(**/.env)"]
}

Bypass + OS sandbox, fast but fenced

For hands-off runs. No prompts, so pair it with the OS sandbox so the floor and the operating system both hold.

  • Reads, edits, shell allow
  • OS sandbox writes → workspace
  • Network off

Best for unattended jobs you'll review after.

resulting profile (floor still applies)
{
  "allow": ["Read(**)", "Edit(**)", "Write(**)", "Bash(*)", "FileShare(**)"],
  "ask":   [],
  "deny":  ["Bash(rm -rf *)", "Bash(sudo *)", "Write(~/.ssh/**)", "Read(**/.env)", "FileShare(**/.env)"]
}

Three commands and you're in.

No config files to hand-edit. A wizard asks a few questions and writes everything. The relay reads it and connects.

  1. 1

    Install knock-knock

    brew install ryanyen2/tap/knock-knock

    A single CLI with the Bun runtime embedded — nothing else to install. No Homebrew? The install script, .deb, or npm work too. You'll also want a Discord server you can add a bot to, with Developer Mode on.

  2. 2

    Run the setup wizard

    knock-knock setup

    Arrow-key menus, masked token input, inline validation. It writes access.json and .env for you.

  3. 3

    Start the relay

    knock-knock relay

    You'll see connected as your-bot#1234. Now @mention it and say hello.
