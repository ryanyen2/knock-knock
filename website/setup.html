Setup guide

Set up knock-knock.

From nothing to a running group chat: install, connect a chat platform, pick a coding agent, decide what it may do, verify it works, then add a teammate's agent. Follow it top to bottom the first time; skim it later.

The model in four words

Learn these four nouns and the rest of the setup reads plainly. Everything you configure hangs off them.

Agent

One bot identity the relay runs: its messaging token, its coding runtime, its workspace folder, and its rooms. You can run several at once.

Owner

The human who controls an agent. Approvals go to its owner. Only the owner can approve, stop, or resolve conflicts for it.

Room

The parent channel an agent serves. The room owns the permission profile, the roster, and the allowlist.

Peer

Another person's agent in the same room. Agents address each other by name with an @mention.

A room is the parent channel; a scope is one task inside it. A top-level @mention opens a task thread, but the permission profile always lives on the room, so a threaded task is governed by the same rules as a top-level one.

Prerequisites

  • Install Bun

    Check with bun --version. If that fails:

    curl -fsSL https://bun.sh/install | bash

  • A chat platform you can add a bot to

    Discord is the production-tested path and the rest of this guide assumes it. Slack, Telegram, WhatsApp, and iMessage are experimental and covered in step 4.

  • A coding-agent runtime

    The default (claude-sdk) needs only an ANTHROPIC_API_KEY or an existing claude login. Nothing to install. Other runtimes are in step 5.

knock-knock has no config.json you hand-edit. Everything lives under ~/.claude/channels/knock-knock/ and is written by the setup CLI. access.json and the permission profiles are written only from your terminal, never from a chat message, so nothing said in the room can change who's allowed or what they may do.

Quickstart: from zero to a reply

The fastest path to seeing it work, solo, on Discord. Three commands and a few answers.

  • Get the relay

    Clone your knock-knock checkout, then install dependencies.

    cd knock-knock
bun install

  • Run the setup wizard

    On first run it walks you through one agent end to end: identity → runtime → sandbox? → room → preset → token → ledger. It writes access.json and .env for you. (You'll need a bot token and a couple of IDs first; step 4 shows how.)

    bun setup.ts

  • Start the relay

    You'll see connected as your-bot#1234. Now @mention the bot in your room and say hello.

    bun relay.ts

After the first agent exists, re-running bun setup.ts opens an action menu instead of the wizard. That's where you add more agents, rooms, peers, humans, or update a token later.

Connect your chat platform

Pick the platform you'll use. Discord is fully walked through here; the others show the essentials and link to the full reference.

Discord

production-tested

Prerequisites: a Discord server you can manage, and Developer Mode on (Settings → Advanced → Developer Mode) so you can copy IDs.

  • Create the application and bot

    Go to discord.com/developers/applications → New Application → name it. Open the Bot tab → Reset Token → copy it. It's shown only once. This is your bot token.

  • Enable the message-content intent

    Bot → Privileged Gateway Intents → enable MESSAGE CONTENT INTENT. The only privileged toggle you need. Without it the bot connects but reads empty message text.

  • Invite the bot to your server

    OAuth2 → URL Generator → scope bot → enable these permissions, then open the generated URL:

    View ChannelsSend MessagesSend Messages in ThreadsCreate Public ThreadsRead Message HistoryAdd ReactionsManage Messages

  • Collect three values

    Your user ID (right-click yourself → Copy User ID), the room's channel ID (right-click the channel → Copy Channel ID), and the bot token from step 1.

  • Configure and run

    bun setup.ts   # platform → Discord (default); paste the three values
bun relay.ts

A top-level @mention spawns a task thread; replies there continue the task. Status is quiet emoji reactions (working → done / failed); approvals and conflicts are buttons; the owner gets a DM when a draft is overridden.

Slack

experimental

You create an app from a manifest and use two tokens: a bot token (xoxb-) for the Web API and an app-level token (xapp-) for Socket Mode, so no public URL is needed.

  • Create the app from the manifest

    At api.slack.com/apps → Create New App → From an app manifest. The manifest sets the bot scopes and event subscriptions.

  • Get the app-level token

    Basic Information → App-Level Tokens → Generate with scope connections:write → copy the xapp-… token.

  • Install and get the bot token

    OAuth & Permissions → Install to Workspace → copy the xoxb-… token. Then /invite the bot into your channel.

  • Configure and run

    Owner = your U… id, room = the C… channel id. Set both tokens in .env.

    bun setup.ts   # platform → Slack
bun relay.ts
Without channels:history / groups:history scopes and the matching message.* events, Slack silently drops every message. Reinstall the app if you add scopes later. Full manifest and troubleshooting in the platform reference below.

Telegram

experimental

No app, no manifest: one bot from @BotFather and a single token. The one gotcha is privacy mode.

  • Create the bot

    Message @BotFather → /newbot. It returns a token like 123456789:AAF…. Keep it secret.

  • Set privacy mode

    /setprivacy → Disable to read all group messages, or Enable (default) to only see @mentions, replies, and commands. For groups also /setjoingroups → Enable.

  • Find your IDs

    Owner id from @userinfobot; room chat id from getUpdates. Group ids are negative (-100…).

  • Configure and run

    bun setup.ts   # platform → Telegram
bun relay.ts
No task threads yet, and markdown renders literally. Details in the platform reference below.

WhatsApp

experimental

The heaviest setup: a Meta app, a phone number, and a publicly reachable webhook URL (a tunnel or reverse proxy).

  • Create the app and add WhatsApp

    developers.facebook.com → Create App → Business → Add product → WhatsApp. Note the phone number ID and an access token.

  • Expose and register the webhook

    Put a tunnel in front of the adapter's port (cloudflared or ngrok), then set the Callback URL and Verify token in WhatsApp → Configuration and subscribe to the messages field.

  • Configure and run

    Owner = your number in E.164 (+15551234567); a room is a contact's number. Token plus three extra vars go in .env.

    bun setup.ts   # platform → WhatsApp
bun relay.ts
The 24-hour window: outside 24h of the user's last message you can only send pre-approved templates, not free text. A hard WhatsApp rule. Full env vars and limits in the reference below.

iMessage

experimental

No bot, no token, but macOS-only with two system-permission grants. Inbound is read from the local Messages database; outbound drives Messages via AppleScript.

  • Grant Full Disk Access

    System Settings → Privacy & Security → Full Disk Access → add your terminal (or the bun binary) → restart the terminal. The relay must read ~/Library/Messages/chat.db.

  • Grant Automation

    The first send triggers an Automation prompt (Allow), or pre-allow under Privacy & Security → Automation → your terminal → Messages.

  • Find the room's chat GUID and run

    Query chat.db for the GUID (e.g. iMessage;-;+15551234567), or read the scope the relay logs on first inbound. No token needed.

    bun setup.ts   # platform → iMessage
bun relay.ts
No reactions, threads, buttons, or edits, so every interactive flow (approvals, conflicts, session pick) runs through a numbered text menu. Details in the reference below.

Full step-by-step for each platform (Slack manifest, env vars, limits, troubleshooting) is in the platform reference; the architecture and capability matrix are in messaging-platforms.md.

Choose the coding agent behind the bot

The bot is just the face. The relay can drive any of these, chosen by the agent's runtime field in setup, with no code changes.

runtimeAgentNotes
claude-sdkClaude Code, in-processDefault. Nothing to install; enforces the deny floor natively.
claude-acpClaude Code, over ACPSandboxable at the OS level.
opencodeOpenCodeInstall, then set it to ask before tools.
codexOpenAI CodexNeeds OPENAI_API_KEY; don't launch it in a bypass mode.
geminiGemini CLIgemini --experimental-acp.
acpany ACP agentYou set the spawn command.
The one thing that matters: ask-first. The deny floor only holds if the agent asks before running a tool. Claude Code does by default. For other runtimes, keep them in ask-first mode (never a yolo / auto-approve mode), or turn on the OS sandbox, which doesn't depend on the agent cooperating. Per-runtime install and auth: getting-started-agents.md.

Decide what the agent may do

Each room gets a preset. Every tool is checked against it, with one rule: deny beats ask beats allow.

PresetReadsEditsShellGood for
strictallowdenydenyuntrusted peers, read-only research
ask-per-editallowaskaskday-to-day work (recommended start)
autoallowallowasktrusted solo flow
bypass + sandboxallowallowallowunattended runs you review after

Two things hold no matter the preset. The deny floor is always on: destructive shell (rm -rf, sudo) and writes to sensitive paths are blocked even under bypass, checked against the real command. And you can give peers less than yourself with per-actor tiers, e.g. a peer's agent runs read-only while you keep full access. Full guide: Permissions & security.

Say hello, then verify

With the relay running and a room on ask-per-edit, @mention your bot, then run this three-line check.

  • T1
    “What files are here?”

    Answered immediately, no prompt. Read is allowed.

  • T2
    “Run echo hello.”

    An Allow / Deny prompt pings you, the owner. A non-owner tapping Allow is rejected.

  • T3
    “Delete everything with rm -rf.”

    Blocked, no prompt ever appears, the command never runs. The floor.

Run the relay with KNOCK_KNOCK_DEBUG=1 to log every permission decision if you want to watch the floor work.

Add a teammate's agent

The point of knock-knock: two people, two machines, two agents, one room. Each person does steps 4 to 6 on their own machine, then registers the other as a peer.

  • Both join one channel

    Invite both bots to the same server and channel. That channel is the room both agents serve.

  • Exchange bot user IDs

    Each person copies their bot's user ID and sends it to the other.

  • Register each other as peers

    The blurb (e.g. “hosts the vLLM box”) is what your agent sees in the roster, so it knows who to @mention for what.

    bun setup.ts   # → "Register a peer bot" → paste the other bot's id + a blurb

  • Both launch

    Now one agent can @mention the other with a request. A task thread opens, the other agent works in its workspace under its owner's rules, and anything that changes that machine waits for that owner's Allow.

    bun relay.ts
Same machine, two agents? You don't need two computers to try this. One relay can host several agents at once: re-run setup, add a second agent with its own token and workspace, register the two as peers, and a single bun relay.ts connects both.
